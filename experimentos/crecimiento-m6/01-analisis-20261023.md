## Auditoría de los archivos

- Los 20 JSON y sus logs están presentes. k6 terminó con código 0 en las 20 corridas.
- En total hubo **321.106 respuestas HTTP 200 de GET /api/tasks**, con **642.212 checks funcionales correctos** y **cero fallidos**. Las 2.120 solicitudes HTTP adicionales corresponden a los logins de preparación (30+50+100+150+200 usuarios, cuatro veces).
- `http_req_failed.value` fue **0** en las muestras revisadas; el resumen que calcula nuestro script lo muestra como `null` porque busca un campo `rate` que este formato no exporta. No confundir `null` con una tasa de fallos medida.
- **Limitación relevante:** el JSON no exportó `http_req_duration{operacion:consulta_tareas}`. Por eso los p50/p95 de arriba son de `http_req_duration`, que también incluye los logins. No son percentiles exclusivos de GET. Los conteos de GET y sus códigos sí se conservan por separado. La tendencia es útil, pero para afirmar un p95 exacto de GET habría que instrumentar esa submétrica en otra medición.
- El valor 90,75 ms de M2 no es directamente comparable como regresión: se midió otro commit y no se acreditó igualdad completa de las condiciones de máquina/configuración actuales.
- Las capturas de `docker stats` se realizaron **antes y después**, no de forma continua durante la carga; no demuestran cómo se comportó CPU/RAM en el pico. Tampoco se guardó utilización del contenedor generador k6, y `observaciones_maquina` aparece vacío.
- El diseño es de VUs constantes (modelo cerrado), no una tasa de llegada fija. Una meseta de GET/s acompañada de latencia creciente **sugiere un límite de capacidad del conjunto evaluado**, pero no identifica si se debe a la API, PostgreSQL, Docker, red o generador.

## Valoración del experimento

**Ejecución completada y checks correctos. Resultado de rendimiento observado, con límites de instrumentación.** Los percentiles reportados son agregados y la saturación del generador no quedó descartada. No presentar las 20 corridas como prueba concluyente de un cuello de botella específico.

Para profundizar: capturar percentiles exclusivos de GET y métricas continuas de API, base de datos, host y k6. No modificar esta evidencia original para acomodar conclusiones.
